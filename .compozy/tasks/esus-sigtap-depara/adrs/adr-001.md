# ADR-001: Catalog-first unified de-para with dual consumption

## Status

Accepted

## Date

2026-07-26

## Context

SIMPA imports e-SUS APS analytical reports where many procedure sections use fixed catalog labels without SIGTAP codes (e.g. "Procedimentos / Pequenas cirurgias", odontological "Procedimentos"), while other sections already embed SIGTAP codes in the description (e.g. "Outros procedimentos (SIGTAP)"). The municipality has spreadsheet bases mapping catalog labels to SIGTAP and needs them persisted, editable via CRUD, documented, and consumed by both future/export production flows and analytical cross-checks against SIA. Planning/billing staff will maintain the mappings. Unmapped items must be silently skipped in MVP processing.

## Decision

Adopt **Approach A — Unified catalog + dual-flow consumption**: deliver a single maintained de-para catalog seeded from the provided spreadsheets plus native SIGTAP sections; provide CRUD for Planning/billing; ship in-app help plus repository documentation describing how export and analytics consume the mapping; in the MVP, both procedure export and analytical cross-reference use the same mapping, silently ignoring unmapped labels.

## Alternatives Considered

### Alternative 1: Catalog + analytics now; export only documented (Approach B)

- **Description**: Ship CRUD, seed, docs, and dashboard cross-reference; defer actual export file generation to Phase 2.
- **Pros**: Faster MVP; lower risk of incomplete export semantics.
- **Cons**: Does not deliver the requested export capability in the MVP.
- **Why rejected**: User selected Approach A to cover both export and analytical use in the MVP.

### Alternative 2: Full governance suite (Approach C)

- **Description**: Approach A plus coverage reports, change history, and official SIGTAP table validation.
- **Pros**: Stronger operational control and auditability.
- **Cons**: Extra scope beyond first operational use; delays core value.
- **Why rejected**: YAGNI for MVP; deferred to later phases if needed.

## Consequences

### Positive

- One source of truth for label → SIGTAP used by export and analytics.
- Planning/billing can correct mappings without engineering changes.
- Documentation exists both for operators (in-app) and for implementers of the export pipeline (repo).

### Negative

- MVP export will be a minimal useful output, not a full BPA/DATASUS suite.
- Silent skip of unmapped items can hide coverage gaps until a later phase adds visibility.

### Risks

- Truncated or incomplete SIGTAP check digits in source spreadsheets may seed wrong codes — mitigate by validating against official SIGTAP when loading seed and allowing CRUD corrections.
- Native SIGTAP sections duplicated with catalog mappings could confuse maintainers — mitigate with clear origin/type on each record and docs.

## Implementation Notes

Seed from user-provided bases for catalog sections; ingest/parse native "código - descrição" rows from e-SUS SIGTAP sections into the same catalog for unified consultation. Export and consolidator/analytics must share the documented lookup contract (exact section + label → active SIGTAP code).
