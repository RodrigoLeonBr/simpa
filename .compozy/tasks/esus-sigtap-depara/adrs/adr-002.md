# ADR-002: Dual-table persistence — procedimentos + e-SUS link

## Status

Accepted

## Date

2026-07-26

## Context

The PRD requires a durable e-SUS label → SIGTAP mapping with CRUD. The product plan already foresaw a master `procedimentos` table (SIGTAP code, description, type, reference table). A single flat de-para table would duplicate SIGTAP metadata and diverge from that plan; a procedures-only table without an e-SUS link cannot key exact `(secao, descricao)` lookups used by `esus_indicadores_raw`.

## Decision

Persist two PostgreSQL tables:

1. **`procedimentos`** — master SIGTAP (and related) procedure catalog: `codigo_sigtap`, `descricao`, `tipo`, `tabela_referencia`, `status`.
2. **`esus_procedimento_map`** — link from e-SUS catalog row to `procedimentos`: `secao`, `descricao_esus` (exact match to raw import), `procedimento_id`, `origem` (`seed` | `nativo_sigtap` | `manual`), `status`.

Unique active mapping per `(secao, descricao_esus)`. Soft-delete via `status = 'inativo'` matching `unidades_saude` / `equipes`.

Initial data via versioned SQL file `seed_esus_sigtap_depara.sql` (no admin upload in MVP).

## Alternatives Considered

### Alternative 1: Single table `esus_sigtap_depara`

- **Description**: One row holds secao, label, codigo_sigtap, origem, status.
- **Pros**: Simpler schema and CRUD.
- **Cons**: Duplicates SIGTAP master concept; harder to reuse codes for emendas/OCI later.
- **Why rejected**: User chose dual-table model aligned with planned `procedimentos`.

### Alternative 2: Only `procedimentos` with e-SUS columns inline

- **Description**: Store secao/label on the same row as SIGTAP code.
- **Pros**: One table.
- **Cons**: Breaks when one SIGTAP code maps from multiple e-SUS labels/sections; conflates master and link.
- **Why rejected**: User chose explicit link table.

## Consequences

### Positive

- Aligns with `estrutura_simpa.md` master-data plan.
- One SIGTAP procedure can be linked from multiple e-SUS labels if needed later.
- CRUD can edit link and/or master procedure fields clearly.

### Negative

- Two entities to seed and maintain; UI must join for list views.
- Slightly more API surface than a flat table.

### Risks

- Truncated check digits in municipal bases — curate in SQL seed; allow CRUD fix.

## Implementation Notes

Follow soft-delete and RETURNING patterns in `simpa-backend/src/routes/cadastros.js`. Extend schema in `schema_full.sql` (or additive migration SQL). Seed populates `procedimentos` first, then `esus_procedimento_map`.
